Build production agents with computer use, the Skills API, and the Files API

Original Link

TL;DR

Anthropic 宣布 Claude Platform 上的 computer use、browser use tool、Skills API 和 Files API 全部进入 GA，并把它们包装成一条“生产级 agent 工作流”叙事：agent 既能看屏幕和网页做操作，也能按团队 skill 执行流程、读取/生成文件、再把结果写回系统。对 agent builder 来说，这比单独放一个新 API 更像是把整套执行面补齐。

Key Points

  • computer use 从单步调用走向 multi-action turns，Anthropic 明说这样能减少 model calls、缩短任务时间，并把该能力放进 HIPAA-regulated workload 适用范围。
  • 新的 browser use tool 在 screenshot 之外加入 page structure，让 agent 在 web app 里能按 field/button 语义定位，而不是只靠像素点击。
  • Skills API 把团队专用 instructions、scripts、templates 变成可上传、可版本化、按需加载的 skill folders，目标是把“专家流程”从 prompt 习惯升级成可复用平台资产。
  • Files API 则提供长生命周期文档存储与输出回传能力，Anthropic 还特别提到自动过期、5x rate limits 和每组织 1 TB storage。
  • 官方用 claims agent 举例：读取理赔文档、加载 filing procedure skill、在保险门户里完成提交、再把确认文件写回；这说明 Anthropic 正在主推“API 少但 UI 多”的企业流程自动化场景。

Why It Matters

这篇的重要性在于 Anthropic 终于把 agent execution stack 讲成了一组可以组合的正式产品表面，而不是零散 preview capability。尤其 browser use + skills + files 这套组合，很明显是在对准那些没有完整 API、但有大量网页和文档流程的 enterprise automation 机会。

My Take

我给 high importance。真正值得关注的不是“又多了几个 API”，而是 Anthropic 在把 production agent 的最难几块拼起来：可操作软件界面、可复用团队知识、可进出文件、可在 sandbox 中执行。保留意见是，官方案例里关于 cost/latency/completion 的数字还很有限，GA 并不等于大规模稳定；但方向已经很明确，就是要把 agent 从 chat surface 推向业务系统执行层。

How monday.com transformed its platform into an agent-first product where humans and agents collaborate

Original Link

TL;DR

Anthropic 这篇 partner case study 讲的是 monday.com 为什么不再满足于在旧工作流上撒一点 "AI dust"，而是直接把平台重构成 human-agent collaboration system。自 2026-05 上线新版以来，monday 表示客户已经在平台上完成了 500 万次 agent interactions；Claude 被嵌进 board、permissions、workflows 和 governance 里，agents 不再是旁路聊天框，而是 workflow 内的 teammate。

Key Points

  • 转折点来自所谓的 "AI dust ceiling"：早期 AI features 有采用，但没有形成持续 usage，于是团队决定从 "给现有产品加 AI" 改成 "把产品原生做成 agent-first platform"。
  • monday 把 agents 设计成带名字、头像、权限和提及入口的 teammates，可覆盖 IT ticket triage、HR 招聘协同、营销竞品情报、以及 Chief of Staff 式运营工作。
  • 文中给出四种 Claude 接入形态：monday Agents、Bring Your Own Agent 接入 Claude Managed Agents、Agents Store 里的预置 agents，以及把 Claude Coding 连到 monday dashboard 的 coding workflow。
  • 一个典型链路是 campaign board item 内从 brief 到 landing page：Strategist Agent 结构化 brief，Landing Page Builder 在自有环境里生成页面，Brand Reviewer 做 brand/legal review，最后人类经理决定 publish or refine。
  • monday 总结的五点 lesson 很实在：最难改的是 mental model；变化期小团队更快；adoption 取决于 trust/gov/permissions；capability 需要数据基础设施匹配；以及最好延展已有产品承诺，而不是凭空造一个 AI 外挂。

Why It Matters

这类文章的价值不在 "某公司用了 Claude"，而在它公开了一个比较完整的 agent-first 产品重构范式。相比单点 copilots，这里更接近 workflow substrate 重写：把 context、governance、assignment、handoff、review 和 execution 都嵌回系统本身。对追踪 agents 的读者来说，这是比单条 benchmark 或 feature release 更有参考价值的产品架构信号。

My Take

我会给 medium importance，但信号质量高于普通 customer story。最值得看的是它承认 "AI dust" 不够，真正的 product advantage 需要把 workflow、权限和数据层一起重做，甚至还专门提到为 agent volume 重投了 monday DB。这比单纯吹 500 万次 interactions 更说明问题。保留意见是：文中没有 retention、task success 或真实 ROI 的硬指标，所以更适合当 platform redesign playbook，而不是效果证明。

Claude on call: How Claude Tag serves as Anthropic’s first responder for CI/CD failures

Original Link

TL;DR

Anthropic 把 Claude Tag 变成了 CI/CD on-call 的 first responder：它在 Slack 里持续监听告警、调用 Grafana / GitHub / Kubernetes / PagerDuty 等工具并行排查，通常 15 分钟内给出首份 SITREP，最快 4 分钟命中 root cause。核心不是一个“会聊天的 bot”，而是一套带 memory、skills、connectors、dynamic workflows 的 incident-response system。

Key Points

  • Claude Tag 挂在 on-call Slack channel 上，持有跨事件 memory，并通过 natural language schedules 触发例行 handoff / 巡检任务
  • 告警检测是 deterministic rules + Claude 辅助调参；真正的 triage 则由 orchestration agent 拉起多个 executor subagents 并行查 Grafana、logs、PagerDuty、GitHub、Kubernetes 和 incident channels
  • Anthropic 记录的实际收益是：每次 incident 基本都有 instant first responder，首份 evidence-grounded analysis 通常 15 分钟内产出，最快 4 分钟给到 root-cause 假设
  • 团队把 oncall instructions、bug-class playbooks、lessons learned 都放在 markdown skills / lessons.md 里，像维护代码一样维护 incident knowledge base
  • 修复层面并不是完全放飞自动化，而是让 Claude 产出 PR、给出 feature-flag 回滚建议、做验证与 handoff，再由人 review / merge / deploy

Why It Matters

这篇文章把“AI agent 进生产”讲得比大多数营销稿更具体：不是泛泛谈 Copilot 提效，而是把 incident response 这个高压、高并发、强上下文场景拆成 detection / triage / resolution / verification 几段，并说明哪些环节 deterministic、哪些环节 agentic。对做 engineering agents 的人，这比 benchmark 更有参考价值。

My Take

我的判断是，这类 on-call agent 的真正壁垒不在模型本身，而在 context engineering + tool surface + org process。Anthropic 这里最值得学的不是“Claude 也能值班”，而是他们把 skills、lessons.md、channel memory、subagents orchestration 和 human review 串成了一个闭环。代价是系统搭建和权限治理要求不低，所以这更像 Team / Enterprise 的范式，不是个人 CLI agent 直接复制就能成功。

Claude models explained: choosing the best model for your use case

Original Link

TL;DR

Anthropic 在 2026-07-24 发这篇文章，目的不是宣布新模型，而是统一它当前模型族的选型口径。最核心的 advice 很直接：默认先从 most intelligent generally available model 开始，再用 effort level 去调成本和延迟，而不是一上来为了省 token 先选小模型。理由是更强模型往往能用更少 turns、thinking time 和 retry 完成任务，真实 cost-per-task 反而更低，也更容易分辨问题到底出在模型还是 setup。

Key Points

  • 文章把选型问题从“价格/参数量”转成了 workload fit：先问 intelligence requirement、latency sensitivity、cost ceiling，再决定是否往下切型号
  • Anthropic 对模型族做了职责划分：Mythos / Fable 面向更高上限与长时程难题，Opus 面向 reasoning-intensive enterprise work，其他层级则更多服务成本或速度约束
  • 一个反直觉但很实用的判断是：小模型虽然 unit price 低，但常常因为出错、返工和 debugging 成本，导致整体 task cost 更高
  • 文章也承认另一种方向存在：组织也可以从最便宜模型往上试，但前提是你已经有清晰的 quality bar 与 eval 方法
  • 整体基调是把 model selection 当成 ops / eval 问题，而不是单次采购决策

Why It Matters

对跟踪 lab 动态的人来说，这篇不是 headline news，但它暴露了 Anthropic 想让客户如何理解其产品线。随着模型等级和 effort knobs 越来越多，真正影响 adoption 的不只是“模型强不强”，而是用户能不能形成稳定的 routing 与 evaluation 方法。

My Take

我会给 medium importance。它的价值主要在 practical framing，而不是信息增量。最值得注意的是 Anthropic 把 cost-per-task 讲得非常明确，这跟 enterprise deployment 的真实指标更一致。弱点也明显：文章更像选型原则说明书，缺少跨行业 workload 的具体 decision table，所以真正落地仍需要团队自己补 eval。

The new rules of context engineering for Claude 5 generation models

Original Link

TL;DR

这篇 2026-07-24 的 Claude 博客不是在讲“prompt 再写长一点”，而是在讲 Claude 5 generation models 上下文设计范式的迁移：Anthropic 说他们把 Claude Code system prompt 砍掉了 80% 以上，却没有 measurable eval loss。核心判断是 newer models 的 judgment 已经足够强，很多旧时代靠 rules、examples、重复说明堆起来的 prompt engineering，应该让位给更轻的 context、表达更好的 tools，以及 progressive disclosure。

Key Points

  • 文章把 context engineering 定义成 system prompt、Skills、CLAUDE.md、memory 等跨请求共享上下文的总和，而不是单次 prompt 优化
  • 最鲜明的结论是“less prompt, more judgment”：以前为了防 worst-case behavior 需要写死很多 guardrails，现在更应该让模型根据周围代码风格和任务语境做判断
  • Anthropic 明确反对一些旧习惯，包括给太多 tool examples、把所有规则 upfront 塞进主 prompt、在多个地方重复同一条指令
  • 替代方案是更重视 interface design 与 progressive disclosure，例如把 verification / code review 放进可按需加载的 skills，而不是长期占用主上下文
  • 文章还点出 memory、artifacts、skills 已经替代 CLAUDE.md 承担部分长期上下文职责，意味着 agent 运行时上下文正在变成更结构化的系统能力

Why It Matters

这篇对 agent builder 的意义很实际。很多团队还在用 2024-2025 年的 prompt discipline 去约束 2026 代模型，结果是 system prompt 越写越肥、工具越加越难用、冲突规则越来越多。Anthropic 这里给出的不是抽象哲学，而是内部 prompt 退场、tool/skill/interface 上位的产品化经验。

My Take

我会给 high importance，但更偏 practical high than headline high。最值得抄的是它把“删规则”说成一种能力升级，而不是偷懒；这跟很多 agent stack 的真实演化方向一致。需要保留的判断是：这类结论只在模型 judgment 足够强、tooling 足够好时成立；如果团队底层接口烂、验收标准模糊，删 prompt 只会把问题暴露得更快。

How Outtake built a cyber investigator on Claude

Original Link

TL;DR

Anthropic 用 Outtake 的案例具体展示了一个 long-running cyber investigator 怎么落地：Recon Agent 不只是读 threat intel，而是会沿着仿冒域名、假 Telegram 支持账号、登录流转向等线索持续追踪对手基础设施，单次 session 中位数 16 分钟、常见会拉到 1 小时以上，最长已跑到 2 小时。技术路线也很明确：先用 Claude Code 把调查流程原型化，再迁移到 Claude Agent SDK，把 memory / context / filesystem 控制收回来，同时保留 coding agent 的 improvisation 能力。

Key Points

  • Outtake 不是只做单点告警，而是把 public intel、brand impersonation 和 internal access 三段攻击链串起来，让 agent 追整张 adversarial graph
  • 团队先手工跑真实调查，定义 what good looks like，再把这个标准逐步交给 agent，避免一开始就把 workflow 机械脚本化
  • Claude Code 被用作第一代 harness，因为 agent 需要写代码、运行代码、临时造工具，并直接与恶意站点交互验证凭证会被送去哪里
  • 生产化阶段转向 Claude Agent SDK，但保留 Claude Code 形成的 patterns，用更细粒度的 memory、context、filesystem control 支撑长时程会话
  • 最关键的是 eval loop：agent 会自己提出“缺什么工具才能查得更好”，另一个 coding agent 根据建议写工具并补测试，人工只在末端判定结果是否变好

Why It Matters

这篇最有价值的部分是它把“长时程 agent”从抽象架构讨论拉回到攻防一线：真正难的不是让模型说出分析结论，而是让 agent 在陌生、高噪声、对手会变招的环境里持续收集证据、改造工具、保持轨道。对安全团队来说，这比泛泛的 agent 叙事更接近真实部署压力。

My Take

我会把它看成 Claude Code -> Agent SDK 的一个很实操的迁移样本。亮点不是又一个 customer story，而是他们明确把 orchestration 约束、开放式 coding capability、filesystem memory 和 eval-driven tool growth 拼成一套闭环。保留意见也要写清：文章给了不少架构 intuition，但对误报率、调查失败模式和安全边界仍讲得不够细。

The evolution of agentic surfaces: building with Claude Managed Agents

Original Link

TL;DR

Anthropic 推出 Claude Managed Agents，一套 production-grade 的 agent 托管基础设施。核心卖点是 'decouple brain from hands'——harness 和 sandbox 分离运行，解决 credentials 安全隔离、session 持久化、latency 和 scaling 问题。适合想快速从 prototype 到 production 的团队，不用自己搭 agent infra。

Key Points

  • Architecture: 'brain' (harness) 和 'hands' (sandbox) 分离，session 作为 append-only log 连接两者，credentials 通过 Vault 管理，永远不进入 sandbox
  • Latency 优化: Claude 立即开始 reasoning，sandbox 并行启动，time-to-first-token 降低 60% (p50) 到 90%+ (p95)
  • Session persistence: 完整 event history，支持 pause/resume，自带 observability console 和 Memory/Dreaming 功能
  • 部署选项: Anthropic-managed cloud 或 self-hosted sandbox (VPC 内)，MCP tunnels 连接私有网络内的 MCP servers
  • Harness 自动演进: 提到 Sonnet 4.5 的 'context anxiety' 问题在 Opus 4.5 消失，Managed Agents 的 harness 会随 model 更新自动调优
  • Customer cases: Notion (12小时→20分钟)、Rakuten (一周内上线多个 specialist agents)、Sentry、Asana、Atlassian

Why It Matters

这是 Anthropic 从 'tokens in/out' API 向 fully managed agent platform 的关键演进。对开发者来说，agent infra (sandbox、session、credentials、observability) 是重复劳动，Managed Agents 让你专注 context 和 domain expertise。对竞争对手，这是 Anthropic 在 agent infra 层的护城河——harness tuning 需要模型团队深度配合，不是随便能复制的。

My Take

文章质量高，技术细节实在。'decouple brain from hands' 是正确的架构选择，解决了 container-based agent 的核心痛点。但要注意：这是 vendor lock-in 加深的产品——你越依赖 Managed Agents 的 harness、Vault、session format，迁移成本越高。对于有强合规需求或想保持 infra 控制权的团队，self-hosted sandbox + MCP tunnels 是关键卖点。另外文章暗示了 Sonnet 4.5 和 Opus 4.5 的存在，值得注意模型命名变化。

Zero Trust for AI agents

Original Link

TL;DR

Anthropic 发布企业级 AI agents 安全部署框架，将传统 Zero Trust 原则适配到 agentic systems。核心论点：AI 模型已将漏洞到攻击的时间从 months 压缩到 hours，agents 的自主性带来新的攻击面，需要 cryptographically rooted identities、per-task permissions、memory protection 等新架构。

Key Points

  • AI-accelerated attacks 已成现实：模型能发现传统工具和人类审查多年遗漏的漏洞，攻击者可利用 AI 加速漏洞利用开发
  • Agents 特有威胁包括：prompt injection、tool poisoning、identity/privilege abuse、memory poisoning、supply chain attacks
  • 提出三 tier Zero Trust 框架：Foundation → Advanced → Optimized，按组织成熟度和风险容忍度分层
  • 八阶段实施流程覆盖：identity、access scoping、sandboxing、input/output controls、memory safeguards
  • 引入 Agentic SOAR 概念：defensive operations 需要与 autonomous attackers 速度匹配
  • 合规对齐覆盖 healthcare、finance、government 等受监管行业

Why It Matters

Multi-agent coordination patterns: Five approaches and when to use them

Original Link

TL;DR

Anthropic 系统性梳理了五种 multi-agent coordination patterns：Generator-Verifier（质量把关）、Orchestrator-Subagent（层级分工）、Agent Teams（并行独立任务）、Message Bus（事件驱动）、Shared State（协作共享）。核心建议是从最简单的 pattern 开始，观察瓶颈再演进，而非一上来就追求复杂架构。

Key Points

  • Generator-Verifier：最简单也最常用，适合 code generation、fact-checking 等有明确 evaluation criteria 的场景，但 verifier 质量决定整个系统的上限
  • Orchestrator-Subagent：Claude Code 使用的模式，适合 task decomposition 清晰的场景，但 orchestrator 会成为 information bottleneck
  • Agent Teams：worker 持久化运行、积累 context，适合 codebase migration 这类独立长任务，但要求任务间 truly independent
  • Message Bus：适合 event-driven pipeline 和不断扩展的 agent 生态，但 debugging 和 tracing 难度高
  • Shared State：去中心化，agents 通过 shared store 协作，适合 research synthesis 这类需要实时共享 findings 的场景，但容易陷入 reactive loop

Why It Matters

这是目前最实用的 multi-agent architecture 指南之一。很多团队在构建 agent 系统时要么 over-engineer，要么选错 pattern 导致扩展困难。Anthropic 直接点出每个 pattern 的 structural assumptions 和 failure modes，比如 Generator-Verifier 的 'rubber-stamp verifier' 问题、Orchestrator-Subagent 的信息瓶颈、Shared State 的 reactive loop——这些都是 production 环境中真正会遇到的坑。

My Take

这篇是 practical engineering guidance，不是 research breakthrough。价值在于：Anthropic 把他们自己在 Claude Code 和内部系统中验证过的架构选择公开了，包括 trade-offs 和演进路径。建议直接看文中的 decision table 和 pattern comparison 部分，然后对照自己的 use case。对于正在构建 multi-agent 系统的团队，从 Orchestrator-Subagent 开始这个建议是务实的——它覆盖面最广、coordination overhead 最低。

Common workflow patterns for AI agents

Original Link

TL;DR

Anthropic 系统总结了 production 环境下 AI agents 的三种核心 workflow patterns：sequential（顺序执行）、parallel（并行处理）、evaluator-optimizer（迭代优化）。文章核心观点是：先用 single agent 尝试，不够再上 workflow，选错 pattern 会浪费 latency、tokens 或牺牲可靠性。

Key Points

  • Sequential workflow：适合有依赖关系的多阶段任务（如 draft-review-polish），用 latency 换 accuracy，每个 agent 专注单一 subtask
  • Parallel workflow：适合独立可并行的任务（如多维度评估、代码审查），fan-out/fan-in 模式，需提前设计好 aggregation strategy
  • Evaluator-optimizer workflow：生成+评估分离的迭代循环，适合有明确质量标准的场景（代码生成、技术文档），需设定清晰的 stopping criteria 防止无限循环
  • 核心决策原则：先用 single agent 试，达标就停；不达标再分析短板选 pattern；patterns 可嵌套组合
  • Tradeoffs 清晰：Sequential 加 latency，Parallel 加 cost 和 aggregation 复杂度，Evaluator-optimizer 乘 token 消耗

Why It Matters

这是 Anthropic 官方对 agent architecture 的实战总结，来自与数十个团队的合作经验。对于正在搭建 multi-agent 系统的团队，提供了清晰的决策框架和避坑指南——过度工程化是常见错误，简单 pattern 往往够用。

My Take

文章实用性强，没有 hype，直接讲 tradeoffs 和 when to avoid。核心洞察是 'start simple'——很多团队一上来就搞复杂 orchestration，其实 single agent 加好 prompt 就能解决大部分问题。Evaluator-optimizer 的 stopping criteria 建议很关键，否则容易陷入 token 无底洞。建议配合他们的 white paper 一起看，这篇是精简版。

When to use multi-agent systems (and when not to)

Original Link

TL;DR

Anthropic 官方关于 multi-agent systems 的实战指南，核心观点是：大多数场景下单 agent 就够用，multi-agent 的 overhead（3-10x tokens）往往得不偿失。只有三种情况值得上：context pollution 严重影响性能、任务可并行化、需要 specialization（工具集/系统提示/领域知识）。文章强调 context-centric decomposition 而非 problem-centric decomposition，并推荐了 verification subagent 这一可靠模式。

Key Points

  • Multi-agent systems 的 hidden cost：3-10x token 消耗、更多 failure points、更多 prompt 维护负担
  • 三种适用场景：context protection（隔离无关信息）、parallelization（并行探索更大搜索空间）、specialization（工具集/系统提示/领域知识分离）
  • 关键设计原则：按 context 边界拆分，而非按问题类型拆分——后者会导致 'telephone game' 问题
  • Verification subagent 模式：专门负责测试/验证的 agent，因只需 blackbox 验证而避免 context 传递问题
  • Early victory problem：验证 agent 容易跑几个测试就 declare success，需要显式指令要求完整测试
  • Tool Search Tool 可减少 85% token 使用，在考虑 multi-agent 前值得先尝试

Why It Matters

这是 Anthropic 官方对 multi-agent 架构的务实判断，直接来自生产环境经验。对正在评估 agent 架构的团队来说，这篇文章提供了清晰的决策框架和反模式警示，能避免数月的过度工程投入。文章也暗示了 Claude 内部 Research feature 的 multi-agent 实现思路。

My Take

这篇文章的价值在于'反炒作'——很多团队在 multi-agent 上过度投入，但单 agent + 更好的 prompting 往往就够了。context-centric decomposition 的洞察很实用，verification subagent 模式值得借鉴。不过文章对 orchestrator 的 routing 复杂度讨论偏轻，实际落地时这往往是瓶颈。另外提到 Opus 4.5 作为 orchestrator 能力更强，暗示了 model capability 对架构选择的影响——随着模型变强，multi-agent 的 threshold 会继续上移。

Building Agents with Skills: Equipping Agents for Specialized Work

Original Link

TL;DR

Anthropic 正式发布 Agent Skills 作为 open standard，这是一个将 domain expertise 打包成文件格式的方案，让 general-purpose agents（如 Claude Code）能够快速获得专业能力。核心理念是：与其为每个领域构建 specialized agents，不如构建可复用的 skills 来装备通用 agent。Skills 使用 progressive disclosure 保护 context window，支持 scripts 作为 tools，并与 MCP servers 协同工作。

Key Points

  • Skills 是组织化的文件集合，包含 SKILL.md、文档和可选的 Python scripts，可被 agent 按需访问和执行
  • Progressive disclosure 三层架构：metadata (~50 tokens) → SKILL.md (~500 tokens) → references (2000+ tokens)，只在需要时加载
  • Skills 与 MCP 互补：MCP 负责 external tools/data connections，Skills 负责 domain expertise 和 procedural knowledge
  • 已发布为 open standard，目标是跨平台可移植——同一 skill 应能在不同 AI 平台使用
  • 已在 Financial Services 和 Healthcare/Life Sciences 垂直领域部署，包括 DCF model builder、bioinformatics bundles、clinical trial protocol generation 等
  • Non-developer 可在 30 分钟内用 skill-creator tool 创建首个 skill，降低了 expertise codification 的门槛

Why It Matters

这是 Anthropic 在 agent 架构上的重要范式转变：从 '构建多个 specialized agents' 转向 '构建通用 agent + skills library'。对于追踪 Claude Code 的开发者来说，这意味着扩展 agent 能力的方式从写复杂 tools/scaffolding 变成了编写结构化文档和脚本。Skills 的开放标准化也意味着社区可以共享和复用 expertise，类似 MCP 的生态效应。

My Take

这个方向是对的——把 expertise 从 agent 核心逻辑中解耦，让更新和分享变得更简单。Progressive disclosure 的设计很务实，解决了 context window 的实际痛点。但关键问题是：skills 的质量和维护成本如何？企业是否会愿意分享 proprietary skills？另外，open standard 能否获得足够多的平台采用还有待观察。对于国内开发者，值得关注的是这种 'code as interface + skills as expertise' 的架构是否会成为行业共识。
