Running an AI-native engineering org

Original Link

TL;DR

Claude Code 工程 Director Fiona Fung 分享了团队在 agentic coding 成为默认工作方式后，如何重构 engineering org 的流程：从 six-month roadmap 转向 JIT planning，code review 中 Claude 处理 style/linting/bugs，human 只在 domain expertise 关键处介入，角色边界模糊化（PM 开始写 code，engineer 涉足 design），核心招聘 profile 转向 creative builders 和 deep systems expertise。

Key Points

  • Planning 从 six-month roadmap 转向 just-in-time (JIT) planning：prototype 先行，快速获取 internal user feedback，减少 design docs 和 formal product reviews
  • Context gathering 不再找 code author，而是直接问 Claude，并思考能否自动化该流程
  • Code review: Claude 处理 style、linting、bugs、tests；human review 只在 legal、security、trust boundaries 等 domain expertise 关键处介入
  • Team makeup 角色模糊：PM 用 Claude 写 code，engineer 做 design/content；招聘重点从 raw throughput 转向 creative builders + deep systems expertise
  • 三个核心 metrics：onboarding ramp time 下降、PR cycle time 下降、Claude-assisted commits 比例上升（团队近四个月 100% Claude-assisted）
  • 团队原则：relentlessly dogfood 自己的产品、保持 flat structure、explicit permission to kill obsolete processes

Why It Matters

这是一篇罕见的来自一线 AI 产品团队的真实实践分享，不是理论推演。Claude Code 团队自己就是 agentic coding 的 heavy user，他们的经验对正在或即将引入 AI coding tools 的团队有直接参考价值。文章揭示了 bottleneck 从 '写代码' 转移到 'verification、review、security' 的现实，以及 org structure 如何随之调整。

My Take

内容扎实，有具体 before/after 对比和可操作的 metrics，比一般 thought leadership 文章实用得多。但要注意：这是 Anthropic 内部团队的 best case，他们深度使用自己的产品且有 strong engineering culture。对大多数公司来说，直接复制这些做法可能水土不服——尤其是 'human review 只在关键处介入' 这条，需要团队对 models 有足够 trust 且 review 能力成熟。另外文章未深入讨论 security review 和 compliance 的具体做法，这块是很多 enterprise 的痛点。建议读者重点关注 JIT planning 和 'ask Claude first' 的 context gathering 思路，这两点落地门槛相对较低。

A harness for every task: dynamic workflows in Claude Code

Original Link

TL;DR

Claude Code 推出 dynamic workflows，允许 Claude 动态生成 JavaScript harness 来编排 subagents。核心价值是解决单 context window 下的 agentic laziness、self-preferential bias 和 goal drift 问题，通过独立 context 的 subagents 并行处理复杂任务。

Key Points

  • Dynamic workflows 通过 JavaScript 执行，提供 spawnAgent、waitForAgent 等函数来协调 subagents，每个 subagent 拥有独立 context window
  • 六大核心 pattern：classify-and-act、fan-out-and-synthesize、adversarial verification、generate-and-filter、tournament、loop until done
  • 实用场景包括：大规模 migration/refactor（Bun 从 Zig 到 Rust）、deep research、deep verification、root-cause investigation、triage at scale
  • 可与 /loop 和 /goal 配合实现持续执行；支持设置 token budget；workflows 可保存到 ~/.claude/workflows 或通过 skill 分发
  • 代价是更高 token 消耗，不适合常规 coding 任务；最佳实践是用于高价值复杂任务
  • 提到 Claude Opus 4.8 具备足够智能来动态生成 custom harness

Why It Matters

这是 Claude Code 从 single-agent tool 向 multi-agent orchestration platform 的关键演进。动态生成 harness 意味着 Claude 可以根据任务特性自主设计执行架构，而非依赖预设模板。对于需要大规模并行、adversarial verification、或长期运行的复杂任务，这是质的提升。同时也暗示 Claude Opus 4.8 的 reasoning 能力已达到可信赖的 meta-level 规划水平。

My Take

这篇文章实操价值很高，patterns 部分可以直接作为 prompt engineering 指南。但要注意：Anthropic 没有披露 workflow 执行的具体成本和 latency，实际生产使用需要评估。另外 Bun 的案例来自外部 thread，说明 ecosystem 正在形成。对于中国用户，值得关注的是这种 multi-agent orchestration 思路可以迁移到其他模型/框架。关键词 'ultracode' 作为 trigger word 值得记住。

How CodeRabbit used Claude to build an agent orchestration system

Original Link

TL;DR

CodeRabbit 构建了一个 agent orchestration system，在 Claude Code 生成代码之前插入一个结构化 planning phase。核心洞察：AI 生成的代码经常 compile 通过、tests 通过，但没解决真正的问题——因为开发者假设 AI 懂得上下文，实际上 AI 在填坑时猜错了方向。解决方案是用 Opus/Sonnet/Haiku 分层处理，产出可 review 的 PRD，把错误拦截在写代码之前。

Key Points

  • 失败模式：AI coding 的常见问题是 code that compiles but doesn't solve the problem——late validation 在 AI workflow 里成本极高
  • Orchestration 架构：Opus 负责 strategic direction，Sonnet 负责 structured planning steps，Haiku 处理 narrowly scoped operations，按 eval harness 结果而非猜测分配任务
  • Planning layer 定位：不是替代 Claude Code 的 Plan Mode，而是在它之前的高层 orchestration，把 implicit assumptions 变成 explicit specifications
  • Eval harness 是关键基础设施：CodeRabbit 专门为 plan quality 构建了 evaluation system，用 LLM judges 评分 + 代码执行结果反推 plan 质量
  • 最佳实践：定义 MPP (maximum possible product)、让 Claude 反问 missing assumptions、保存 planning artifacts 作为 shared record

Why It Matters

这篇文章触及了 AI coding 的核心痛点：代码生成越来越便宜，但走错方向的成本越来越高。CodeRabbit 的方案是一个务实的 engineering 解法——不是让 model 更聪明，而是在 workflow 上加 guardrail。对于做 agent system 的人来说，model routing 策略和 eval harness 的思路值得借鉴。文章本身有实质内容，不是 thin marketing piece。

My Take

这个方向是对的，但实现门槛不低。大多数团队没有 CodeRabbit 这种规模（每周 review 2M PRs）来积累数据和构建 eval harness。文章没提的是：这套 orchestration layer 本身的维护成本、planning phase 增加的 latency 是否影响用户体验、以及当 codebase 变化时 plan 多快会过时。核心价值在于 'plan as quality gate' 的理念——把 code review 的一部分工作前移到 plan review。对于 serious engineering org 有参考价值，但小团队可能 overkill。另外注意到文章日期是 May 2026，可能是 future-dated marketing content，需谨慎对待。

Using Claude Code: The unreasonable effectiveness of HTML

Original Link

TL;DR

Claude Code 团队成员分享了一个实用模式：用 HTML 替代 Markdown 作为 agent 输出格式。核心论点是 HTML 提供更高的信息密度、视觉清晰度、易分享性和双向交互能力——当 agent 生成的文档越来越长、你越来越依赖 agent 编辑而非手改时，Markdown 的优势在减弱。

Key Points

  • HTML 信息密度远超 Markdown：支持 tables、CSS、SVG、交互元素、canvas 等，几乎能表达 Claude 能读取的任何信息类型
  • 可读性和分享性：>100 行的 Markdown 文件没人愿意读；HTML 可做 tabs、导航、mobile responsive，直接丢链接就能分享
  • 双向交互：可以让 Claude 生成带 sliders、knobs 的编辑界面，配合 'copy as prompt' 按钮把调整结果贴回 Claude Code
  • Claude Code 的 context 优势：可 ingest 文件系统、MCP (Slack/Linear)、浏览器、git history，比 Claude.ai 更适合生成复杂 HTML 报告
  • 主要 use cases：specs/planning、code review、设计原型、报告生成、custom editing interfaces（如拖拽排序 tickets、编辑 feature flags）

Why It Matters

这揭示了一个 agent 时代的工作流演变：当人类从「编辑文档」变成「审阅 agent 输出 + prompt 调整」时，输出格式的选择逻辑完全不同。HTML 作为 agent-human communication layer 的价值被低估了。对重度 Claude Code 用户，这是可以直接抄的实战模式。

My Take

观点本身有道理，但作者承认自己是 'HTML maximalist'，有过度推广倾向。实际中 Markdown 在快速笔记、git commit messages、简单 specs 场景仍有价值。真正值得采纳的是「复杂输出用 HTML」这个原则，而非一刀切。文中提到的 custom editing interfaces + export pattern（生成一次性编辑器，最后 copy back to prompt）是个很聪明的 tight loop 设计，值得尝试。GitHub gallery 如果有实际模板会更有参考价值。

Lessons from building Claude Code: Prompt caching is everything

Original Link

TL;DR

Claude Code 团队分享了在生产环境中优化 prompt caching 的实战经验。核心观点：prompt caching 是 long-running agents 可行的经济基础，Claude Code 整个架构都围绕它设计，甚至会对 cache hit rate 设告警。文章详细解释了 prefix matching 机制、如何组织 prompt 结构、避免 mid-session 改动 tools/models、以及 cache-safe forking 做 compaction 的技巧。

Key Points

  • Prompt caching 是 prefix matching，任何 prefix 变动都会 invalidate 整个 cache，所以要把 static content 放前面、dynamic content 放后面
  • 不要 mid-session 更换 model 或增删 tools——这会 break cache。用 tools 本身来建模状态转换（如 EnterPlanMode/ExitPlanMode），而非改变 tool set
  • 用 messages 传递更新信息而非修改 system prompt，例如用 <system-reminder> tag 在 user message 里传递时间戳或文件变更
  • Tool search + defer_loading 模式：用 lightweight stubs 占位，model 需要时再 load full schema，保持 prefix 稳定
  • Compaction 要用 cache-safe forking：复用 parent conversation 的 system prompt、tools、context，只在末尾 append compaction request，这样才能复用 cache
  • Cache hit rate 要像 uptime 一样监控，几个百分点的 miss 就会显著影响成本和延迟

Why It Matters

对于构建 agents 的开发者，这是 Anthropic 官方给出的 prompt caching 最佳实践，直接来自 Claude Code 生产环境。这些技巧决定了你的 agent 产品在经济上是否可行——long-running agents 没有 caching 会非常昂贵。文章揭示了很多反直觉的坑，比如 mid-session 换 model 到 Haiku 反而更贵、compaction 调用可能产生巨额 uncached cost。

My Take

Best practices for using Claude Opus 4.7 with Claude Code

Original Link

TL;DR

Opus 4.7 是 Anthropic 目前最强的 coding 和 agentic tasks 模型，但 token 用量和行为与 4.6 有明显差异。本文核心是指导用户如何调优：新增 xhigh effort level 作为默认值、adaptive thinking 替代 fixed thinking budget、以及交互策略从 pair programming 转向 delegation 模式。

Key Points

  • 新增 xhigh effort level（介于 high 和 max 之间）作为默认推荐，平衡 reasoning 能力和 token 成本，避免 max 的 overthinking 问题
  • Adaptive thinking 取代 fixed thinking budget——模型自主决定何时思考、何时跳过，简单查询响应更快，复杂任务才投入 thinking tokens
  • 交互策略转变：把 Claude 当作 capable engineer delegation 而非 pair programmer，第一轮就给足 context（intent、constraints、acceptance criteria），减少 turn 数量
  • Auto mode（Shift+Tab）适合长任务，可让模型自主执行减少 check-in 开销
  • 行为变化：response length 按 task complexity 动态调整（不再默认 verbose）、tool call 频率降低、subagent spawn 更谨慎——如需更多 tool use 或并行 subagent 需显式 prompt

Why It Matters

这篇是 Opus 4.7 的实战调优指南，直接关系到 token 成本控制和 coding 效率。如果你在用 Claude Code 做生产级开发，不调整 effort level 和交互策略可能导致成本超预期或效果不达预期。Adaptive thinking 的引入也意味着 prompt engineering 需要相应调整。

My Take

Anthropic 在 effort level 上做了更细粒度的控制，xhigh 这个档位很务实——max 容易 overthinking 且成本失控，xhigh 是大多数场景的甜点。Adaptive thinking 是正确方向，但用户需要重新学习如何 prompt（想要更多思考要显式说 'think carefully'，想省 token 要说 'prioritize responding quickly'）。整体来看，Opus 4.7 更适合 autonomous agents 而非 interactive coding，这对 agent workflow 设计有指导意义。

Using Claude Code: session management and 1M context

Original Link

TL;DR

这是一篇关于 Claude Code session 管理的实用指南，重点讲解如何在 1M context window 下高效使用 Continue、/rewind、/clear、/compact 和 Subagents 五种策略，以及如何避免 context rot 导致的性能下降。

Key Points

  • Context rot 是真实问题：即使有 1M context，随着 context 增长，model performance 会因 attention 分散而下降，老内容会干扰当前任务
  • /rewind (双击 Esc) 比「纠正式 prompting」更高效：回退到失败尝试前，保留有用的 file reads，用学到的经验重新 prompt
  • /compact vs /clear 的关键区别：compact 让 model 自动总结（有损但省力），clear 由你手动提炼关键信息后重新开始（更精准但费时）
  • Bad autocompact 的根因：model 在 compact 时处于「最不聪明」的状态（context rot 最严重），无法预测你接下来的工作方向，可能丢掉重要信息
  • Subagents 的判断标准：如果只需要结论而不需要中间 tool outputs，就 spawn subagent 让它在独立 context 中工作
  • 核心原则：新任务开新 session，相关任务可延续，主动管理 context 比被动等 autocompact 更可控

Why It Matters

1M context 让长任务成为可能，但也让 context 管理变得 critical。理解这些机制能显著提升 Claude Code 的实际 productivity，避免在关键时刻因 bad compact 或 context rot 翻车。这是目前最系统的 Claude Code workflow 优化指南。

My Take

这篇文章填补了 Claude Code 使用经验的重要空白——官方终于承认 context rot 是真实存在的问题，并给出了具体的 mitigation 策略。实用的启发式规则：主动 compact 带指令 > 被动等 autocompact；rewind > 纠正式对话；subagent 适合「只要结论」的场景。建议重度用户把文中的 decision table 存下来当 cheatsheet 用。
